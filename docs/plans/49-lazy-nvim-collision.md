## 1. 背景 / 現状

### 1.1 再現(実測)

`{ "folke/lazy.nvim", version = "*" }` を含む config を extract すると、**`raw.plugins` に `lazy.nvim` キーが入る**:

```console
$ cat init.lua

  { "folke/lazy.nvim", version = "*" },
  { "folke/tokyonight.nvim" },
})
$ ... nvim --headless --cmd "luafile lua/nvimx/extract.lua" ; jq -S .plugins raw-spec.json
{
  "lazy.nvim": {
    "name": "lazy.nvim",
    "short": "folke/lazy.nvim",
    "url": "https://github.com/folke/lazy.nvim.git",
    "version": "*"
  },
  "tokyonight.nvim": { ... }
}
```

これを resolve に通すと `plugins["lazy.nvim"].inputName == "lazy-nvim"` になり、genflake が `lazy-nvim` を 2 回書く:

```nix
# This file is generated by nvimx. Do not edit by hand.
{
  inputs = {
    lazy-nvim = {
      url = "github:folke/lazy.nvim";
      flake = false;
    };
    lazy-nvim = {
      url = "github:folke/lazy.nvim";
      flake = false;
    };
    tokyonight-nvim = { ... };
  };
  outputs = _: { };
}
```

`nixfmt` はこれを**素通しする**(評価しないので気付かない。実測で 1 バイトも変わらない)。
`lock-app.nix:235-239` は genflake → `nixfmt` → `nix flake lock` の順なので、落ちるのは最後の `nix flake lock` である:

```console
$ nix flake lock
error: attribute 'lazy-nvim.url' already defined at .../flake.nix:5:7
       at .../flake.nix:9:7:
            8|     lazy-nvim = {
            9|       url = "github:folke/lazy.nvim";
             |       ^
```

**プラグイン名もどの spec 行が原因かも一切出てこない**。これが issue の言う "a raw Nix evaluation error naming a duplicate attribute, with nothing pointing at the spec line that caused it" である。

### 1.3 壊れ方は **1 つではなく 2 つ**ある

issue が挙げているのは `folke/lazy.nvim` の場合だけだが、`to_input_name`(`resolve.lua:269-271`)は
`[^%w_-]` を `-` に写す**だけ**なので、`lazy-nvim` に正規化される名前は他にもある。実測:

```console
$ cat init.lua
require("lazy").setup({
  { "someone/lazy-nvim" },
  { "o/lazy_nvim" },
})
$ ... extract ... ; jq -S '.plugins | keys' raw-spec.json
[ "lazy-nvim", "lazy_nvim" ]
```

- `{ "someone/lazy-nvim" }` → 名前 `lazy-nvim` → `to_input_name` は恒等 → **synthetic と衝突する**。
  現行コードで単独でも生成 flake が壊れることを実測済み(`lazy-nvim` が `github:folke/lazy.nvim` と
  `github:someone/lazy-nvim` の 2 回、`nix eval` が同じ duplicate attribute で落ちる)。
- `{ "o/lazy_nvim" }` → 名前 `lazy_nvim` → `_` は `[^%w_-]` に含まれないので保存され、`lazy_nvim` のまま。**衝突しない**。

**この 2 つは根本的に別物である**:

| ケース | ユーザーの意図 | 正しい挙動 |
|---|---|---|
| 名前が `lazy.nvim` | 「**その** lazy.nvim をこう使え」 | 同じ input を再利用し、spec が ref を決める(§3.2) |
| 名前が `lazy.nvim` **ではない**が input 名が `lazy-nvim` になる(`lazy-nvim`, `lazy nvim`, `lazy@nvim` …) | 「別のプラグインを入れたい」 | 予約名との衝突として lock 時に fatal(§3.9) |

issue が要求する「合成エントリを衝突検査に参加させる」は**後者**にしか効かない。前者に同じ扱いをすると、
lazy.nvim 自身のドキュメントが勧める書き方が一律にエラーになる。**本計画は 2 系統に分ける。**

### 1.4 lazy.nvim は「もう 1 つ」持てない — 構造的な理由

「重複を落として同じ input を再利用する」という issue の見立てを、`nix/lib/` 側から裏取りした。

`nix/lib/make-env.nix:42-45` は lazy.nvim の src を **`pluginsDb.lazyNvim.inputName` から**引く:

```nix
  lazyNvimDrv = mkPluginDrv {
    name = "lazy.nvim";
    src = if hasLock then getSource pluginsDb.lazyNvim.inputName else lazyNvimSeed;
  };
```

そして farm は `:122-133` で **`lazy.nvim` という名前のエントリを無条件に先頭に置き**、そのあとに `pluginDrvs`(= `pluginsDb.plugins` 由来)を並べる:

```nix
  farm = mkFarm {
    entries = [
      {
        name = "lazy.nvim";
        path = lazyNvimDrv;
      }
    ]
    ++ lib.mapAttrsToList (name: drv: { inherit name; path = drv; }) pluginDrvs;
  };
```

`pluginsDb.plugins` に `lazy.nvim` が居ると、**farm に同名エントリが 2 つ入る**。`linkFarm` はリストを
`foldl'` で attrset に畳むので **last-wins** であり、エラーにならず**黙って後勝ち**する
(nixpkgs `pkgs/build-support/trivial-builders/default.nix:636-638` の "We do this foldl to have last-wins semantics in case of repeated entries")。
後に来るのは `pluginDrvs` の方なので、**`lazyNvimDrv` が黙って捨てられる**。その結果:

- `resolve-plugin.nix` が lazy.nvim に対しても `plugins.overrides` / `plugins.nixpkgsFallback` / `nix/build-registry/` を適用してしまう。
  これは `make-env.nix:47-48` の *"overrides / nixpkgsFallback only ever apply to plugins from the lock: lazy.nvim itself is nvimx's own foundation, not a plugin the user declared"* と、
  `docs/architecture.md:345` の *"1–3 only ever apply to plugins in the lock; the lazy.nvim seed is nvimx's own foundation and is not overridable"* を**同時に破る**。
- spec の `build` が lazy.nvim 本体に対して走る。
- `bootstrap.lua.in:9` の `vim.opt.rtp:prepend(farm .. "/lazy.nvim")` が指す先が入れ替わる。

**したがって「lazy.nvim を他プラグインと同列に farm へ並べる」は選択肢ではない。**
lazy.nvim は `plugins` の外(= `lazyNvim` キー)に居続けなければならない。issue の見立ては構造的に正しい。

### 1.5 spec のどのフィールドが extract を通過するか(実測)

`extract.lua:110-127` の `dump_plugin` が dump するのは
`name` / `short` / `url` / `dir` / `dev` / `branch` / `tag` / `commit` / `version` / `versionFromDefaults` / `pin` / `build` / `dependencies` / `hasCond` **だけ**である。実測:

```console
$ cat init.lua
require("lazy").setup({
  { "folke/lazy.nvim", branch = "main", build = "make", lazy = false, dependencies = { "folke/tokyonight.nvim" } },
})
$ ... extract ... ; jq -S '.plugins["lazy.nvim"]' raw-spec.json
{
  "branch": "main",
  "build": "make",
  "dependencies": [ "tokyonight.nvim" ],
  "name": "lazy.nvim",
  "short": "folke/lazy.nvim",
  "url": "https://github.com/folke/lazy.nvim.git"
}
```

**`lazy = false` はどこにも現れない。** `priority` / `opts` / `keys` も同じで、これらは lazy の**ランタイムのロード指示**であり、
nvimx はユーザーの lua を一切書き換えない(`docs/architecture.md:121-122`)ので、ランタイムでそのまま効く。
**lock 時に扱うべきものが無い**ので、`lazy = false` については本件で何もしない。

もう 1 つ実測しておいた事実: `{ url = "https://github.com/myfork/lazy.nvim.git" }` は名前 `lazy.nvim` になり、
`url` はフォーク側のまま残る。つまり **`lazyNvim` の source は `folke/lazy.nvim` 固定ではあり得ない**(§3.3)。

### 1.6 既存の衝突検査の実際の挙動

`resolve.lua:674-677` はこうなっている:

```lua
    if seen_inputs[input_name] then
      error(("input name collision: %s (%s / %s)"):format(input_name, name, seen_inputs[input_name]))
    end
    seen_inputs[input_name] = name
```

issue は「既存の衝突エラーの文言・出力経路(`[nvimx] ...`)に合わせよ」と書いているが、**既存の経路は `[nvimx]` ではない**。実測:

```console
$ nvim -l lua/nvimx/resolve.lua collide.json out.json
E5113: Lua chunk: lua/nvimx/resolve.lua:675: input name collision: foo-nvim (foo-nvim / foo.nvim)
stack traceback:
	[C]: in function 'error'
	lua/nvimx/resolve.lua:675: in main chunk
rc=1
```

素の Lua `error()` なので E5113 + traceback が出る。`fail`(`:22-25`)/ `fail_plugin`(`:367-370`)/
`report_resolve_errors`(`:376-390`)のどれも通らない。

**さらに悪いことに、この文言は決定的ですらない。** メインループは `pairs()` で走るので、2 つのうちどちらが
「先に見つかった側」になるかは実行ごとに変わる。同じ入力で 8 回走らせた実測:

```console
      7 ... input name collision: foo-nvim (foo-nvim / foo.nvim)
      1 ... input name collision: foo-nvim (foo.nvim / foo-nvim)
```

これは `plugin_warnings` を名前でソートしている理由(`resolve.lua:412-415` の
*"raw.plugins is traversed with pairs(), so emitting as we go would give the warnings array a different order on every run"*)
と正面から矛盾する既存バグである。**新しい check を素朴に足すと、この非決定性を 1/8 の確率で踏むフレーキーな check になる。**
本件は合成エントリをこの検査に参加させる以上、ここも直す(§3.9)。

## 2. ゴール

issue の "Done when" を検証可能な形に落とす。

1. **spec に `folke/lazy.nvim` を書いた config が lock できる。** 生成 flake は 1 つの `lazy-nvim` input だけを持ち、
   評価が通り、`nix flake lock` が成功する。
2. **ユーザーが書いた `tag` / `commit` / `branch` / `version` / `pin` が実際に効く。**
   「重複を落とすだけ」で pin が黙って無視されることは無い(§3.2 の却下理由)。
3. **`lazy.nvim` ではないが input 名が `lazy-nvim` になるプラグイン(`someone/lazy-nvim` など)は lock 時に fatal**、
   `[nvimx] resolve failed: plugin "..."` の形でプラグイン名を挙げて落ちる。生の Nix 評価エラーには到達させない。
4. **既存の inputName 衝突検査を `[nvimx]` 経路に載せ、出力を決定的にする**(§1.6)。
5. **lazy.nvim は `plugins` の外に居続ける。** farm に 2 つ目の `lazy.nvim` エントリは決して作らない(§1.4)。
6. **#32(locked lazy.nvim を抽出 seed に使う)の設計余地を狭めない。** input 名は `lazy-nvim` のまま、
   lazy.nvim の source は `plugins.json` の中で 1 箇所にしか存在しない(§4.1)。
7. **`docs/plans/23-resolve-semver.md:235` の申し送り(共有 input に semver ゲートが発火するか)に実測で答える**(§3.7)。
8. **`--update` サマリが lazy.nvim を通常プラグインと同じ規則で扱う。** `pin = true` は
   `pinned: ... (skipped)` として報告され、spec 編集による移動は「名前指定なしで動いた」警告の
   **誤検知にならない**(§4.3.1)。
9. **`--import-lazy-lock` の classification 8 が、spec に lazy.nvim があるときだけ通らなくなる**ことを check で固定する(§3.8)。
10. **check `resolve-lazy-self`(新規)+ `resolve-import-lazy-lock` / `update-summary`(ケース追加)が上記を覆う**。
    `nix flake check` が Linux でグリーン、`aarch64-darwin` でも評価できる。**既存 golden は 1 本も再生成しない**(§4.4)。

## 3. 設計

### 3.1 全体像 — メインループの構造と、`lazy.nvim` を除外する **順序**

`resolve.lua:669-825` のメインループは現在 2 分岐(`dev/dir` → `local_plugins` / それ以外 → `plugins`)である。
重要なのは、else 節の**先頭**が input 名の導出と衝突検査になっていることである(`resolve.lua:673-677`):

```lua
    local input_name = to_input_name(name)
    if seen_inputs[input_name] then
      error(...)
    end
    seen_inputs[input_name] = name
```

`to_input_name("lazy.nvim") == "lazy-nvim"` なので、**§3.9 の予約シード
(`seen_inputs["lazy-nvim"] = "lazy.nvim"`)をループ前に置いた瞬間、案 C のメインケースである
`folke/lazy.nvim` 自身が予約名衝突として fail_plugin される。**
したがって「lazy.nvim かどうか」の判定は**衝突検査より前**に来なければならない。行き先の分岐
(`plugins[name] = entry` に枝を足す)を else 節の末尾に置くだけでは足りない。

正しい順序は次のとおり:

```lua
for name, p in pairs(raw.plugins) do
  local is_lazy = name == LAZY_NAME          -- ★ ループの最初に決める
  if p.dev or p.dir then                     -- 既存。ローカルプラグイン。is_lazy より優先(§3.4)
    local_plugins[name] = ...
  else
    local input_name = to_input_name(name)
    if not is_lazy then                      -- ★ lazy.nvim は衝突検査を通さない。
      <衝突検査 / seen_inputs への登録>      --   予約シードが主張しているのは自分自身だから
    end

    -- entry の組み立ては以下すべて共通(source 解析 / merge / pin 凍結 /
    -- import seed / semver ゲート)。is_lazy が効くのは build 警告の抑止と、
    -- build / dependencies を entry に入れないこと(§3.4)の 2 箇所だけ
    local entry = { ... }

    if is_lazy then
      lazy_entry = entry        -- ★ 新規。plugins には入れない
    else
      plugins[name] = entry     -- 既存
    end
    -- §3.9 の `collided` を足すと 3 分岐になる(衝突したものはどちらにも入れない)。
    -- 最終形は §3.10 #8 / §5.1 (d) を見ること
  end
end
```

`is_lazy` を**ループの最初に 1 回だけ計算する**のは、次の **4 箇所**が**同じ判定**を使うことを
構造で示すためである: 衝突検査の除外(ここ)・`build` 警告と `unbuildable` の抑止(§3.4)・
`build` / `dependencies` を entry に入れない分岐(§3.4)・行き先の分岐(ここ)。
4 箇所に `name == LAZY_NAME` を書き散らすと、1 つだけ条件を直したときに
「衝突検査は通すが plugins には入らない」といった中途半端な状態が作れてしまう。

**「1 本のコードパス、2 つの行き先」であることが本設計の要である**
(衝突時はどちらにも入れない第 3 の枝が §3.9 で加わるので、最終形は 3 分岐になる。§3.10 #8 / §5.1 (d))。
`--prev` マージ / `pin` 凍結 / `--import-lazy-lock` seed / semver 解決 / `--update` の force は
すべてこのループとその直後のバッチが担っているので、行き先だけ変えれば `lazyNvim` エントリが
**他のプラグインとまったく同じ規則で**決まる。専用の分岐が要ったのは上の **4 箇所**
(衝突検査の除外 / `build` 警告の抑止 / entry フィールドの除外 / 行き先)だけで、
これは §3.10 の #5 / #6 / #7 / #8 に 1 対 1 で対応する。

出力段では `result.lazyNvim` が `lazy_entry or <従来の合成リテラル>` になる(`resolve.lua:1297-1301`)。
**spec が lazy.nvim を書いていないときの出力は 1 バイトも変わらない**(§6.3 で実測)。

### 3.2 統合の方式 — **spec が input の ref を決める**(採用)。3 案を却下する

issue の見立て(「同じ input を再利用して重複を落とす」)は §1.4 のとおり構造的に正しい。
ただし**「重複を落とす」の解像度が足りない**。3 つの案を検討した。

#### 却下 A: lock 時のエラーで止めるだけ

合成エントリを `seen_inputs` に入れ、`folke/lazy.nvim` も含めて一律 fatal にする。

- **却下理由 1**: `{ "folke/lazy.nvim", version = "*" }` は lazy.nvim 自身のドキュメントが勧める書き方であり、
  issue 本文も "appears in real configs, including in lazy's own docs" と書いている。
  **正しい lua を書いたユーザーに「その行を消せ」と言う**ことになる。消せば config は nvimx 専用になり、
  素の lazy.nvim では lazy が自己管理されなくなる。
- **却下理由 2**: nvimx はもともと `lazy-nvim` input を持っており、ユーザーが書いたのは
  「もう 1 つ寄越せ」ではなく「**その** lazy.nvim をこうしろ」である。技術的に応えられる要求を、
  実装の都合で拒否することになる。
- **却下理由 3**: それでも §1.3 の後者(`someone/lazy-nvim`)には fatal が要る。A を採っても
  「lock 時のエラーで止める」実装は結局書くことになるので、**A は B/C の部分集合**であり、
  節約になるのは fold の分だけである。

ただし issue の "Done when" は "**or** fails at lock time with a message naming the plugin" を許している。
A は最低ラインとしては合格である。本計画が A を採らないのは、上記 1 と 2 が
「#49 が直そうとしている『黙って壊れる』の裏返し(『正しく書いたのに拒否される』)」だと判断したからである。

#### 却下 B: 重複を落とすだけ(spec の ref フィールドは捨てる)

`plugins` から `lazy.nvim` を除き、`lazyNvim` は今までどおりの合成リテラルのまま。

- **却下理由**: `{ "folke/lazy.nvim", version = "^11", pin = true }` と書いたユーザーの `version` も `pin` も
  **黙って消える**。生成 flake は評価できるようになるので、**ユーザーは成功したと思う**。
  これは #49 が直そうとしている「黙って壊れる」問題の、より発見しにくいバージョンである
  (今は少なくとも `nix flake lock` が落ちてくれる)。
  「lock は通ったが lazy.nvim は自分が指定した版ではない」は、いつ気付くかというと**気付かない**。
- B を採るなら最低限「`tag`/`commit`/`branch`/`version`/`pin` を書いたら警告」が要るが、
  警告を出すところまで来ているなら**その値を実際に使わない理由が無い**。

#### 却下 D: 合成 input の名前を衝突回避のためリネームする

`lazyNvim.inputName` を `nvimx-lazy-nvim` などにして、ユーザーの `lazy.nvim` を普通のプラグインにする。

- **却下理由 1**: §1.4 のとおり **farm に `lazy.nvim` が 2 つ入る**。`linkFarm` は last-wins なのでエラーにならず、
  ユーザーのプラグインエントリが nvimx の foundation を黙って置き換える。
  `make-env.nix:47-48` と `docs/architecture.md:345` が明文で禁じている状態が、静かに成立してしまう。
- **却下理由 2**: 既存ユーザー全員の `flake.lock` の input 名が変わる。`nix/lib/sources.nix:11` は
  `rootInputs.${inputName} or (throw "nvimx: input '${inputName}' not found in flake.lock")` なので、
  `plugins.json` と `flake.lock` を両方作り直すまで壊れる。**キー 1 個の衝突回避に払うコストではない**
  (`docs/plans/43-drop-optional-field.md:128` が `schemaVersion` を上げない理由として挙げているのと同じ天秤)。
- **却下理由 3**: #32 が「lock の中の lazy.nvim」を探すとき、`lazyNvim` と `plugins["lazy.nvim"]` の
  **2 つの候補**を相手にすることになる。ゴール 6 に反する。

#### 採用 C: 同じ input を再利用し、**spec が その input の ref を決める**

`plugins` からは除き、`lazyNvim` エントリ側が spec の `source` / `branch` / `tag` / `commit` / `version` / `pin` / `resolvedRef` を持つ。
`genflake.lua:79` を

```lua
inputs[#inputs + 1] = { name = db.lazyNvim.inputName, url = input_url({ source = db.lazyNvim.source }) }
```

から

```lua
inputs[#inputs + 1] = { name = db.lazyNvim.inputName, url = input_url(db.lazyNvim) }
```

に変えるだけで、`input_url`(`genflake.lua:33-76`)の優先順ラダーがそのまま lazy.nvim にも効く。実測(プロトタイプ):

```console
$ # raw-spec: { "lazy.nvim": { url = ".../folke/lazy.nvim.git", tag = "v11.14.1" }, ... }
$ nvim -l resolve.lua raw-ok.json ok.json && nvim -l genflake.lua ok.json ok.flake.nix && cat ok.flake.nix
# This file is generated by nvimx. Do not edit by hand.
{
  inputs = {
    lazy-nvim = {
      url = "github:folke/lazy.nvim/refs/tags/v11.14.1";
      flake = false;
    };
    tokyonight-nvim = {
      url = "github:folke/tokyonight.nvim";
      flake = false;
    };
  };
  outputs = _: { };
}
```

**`lazy-nvim` は 1 つだけ、URL はユーザーが書いた tag を指している。** これが C の全体像である。

`input_url` は `p.source` を見るので、フォーク(§1.5)も自動的に効く。git type の実測は §3.7 にある。

### 3.3 `lazyNvim` エントリのスキーマ

C を採ると `lazyNvim` は「プラグインエントリ から `build` と `dependencies` を除いたもの + `synthetic`」になる。
実測した実際の出力(プロトタイプ、`json.lua` のキー昇順・2 スペース字下げそのまま):

```json
{
  "lazyNvim": {
    "branch": null,
    "commit": null,
    "inputName": "lazy-nvim",
    "pin": null,
    "resolvedRef": null,
    "source": {
      "owner": "folke",
      "repo": "lazy.nvim",
      "type": "github"
    },
    "synthetic": false,
    "tag": "v11.14.1",
    "version": null
  },
  ...
}
```

キーの取捨は**読み手から逆算して**決めた:

| キー | 誰が読むか | 載せるか |
|---|---|---|
| `inputName` | `genflake.lua:79`、`make-env.nix:44`、`update-summary.lua:146-148`、`resolve.lua:1324` | **必須** |
| `source` | `genflake.lua:34-50`(`input_url`) | **必須** |
| `commit` / `resolvedRef` / `tag` / `branch` | `genflake.lua:37-64`(`input_url` の優先順ラダー) | **必須** |
| `version` | `same_identity`(`resolve.lua:277-278` の `identity_fields`)。マージ契約が `version` の変更で `resolvedRef` を捨てるため | **必須** |
| `pin` | `resolve.lua:735`(pin 凍結の条件) | **必須** |
| `synthetic` | 誰も読まない(`grep -rn lazyNvim` で確認)。`docs/architecture.md:189` が文書化している | **載せる**。`true`=nvimx が決めた / `false`=spec が決めた の区別は #32 と人間にとって有用で、値は 1 箇所でしか作られない |
| `build` | `make-env.nix:42-45` は `mkPluginDrv` に build を渡していない = **読まない** | **載せない**(§3.4) |
| `dependencies` | 誰も読まない。`resolve.lua:334` が *"Dependencies are recorded for reference only"* と明記 | **載せない**(§3.4) |

**`schemaVersion` は 1 のまま。** `docs/plans/43-drop-optional-field.md:112-128` が確立した基準
(「追加は additive、削除は additive でない」「上げると既存ユーザーの committed plugins.json が読めなくなり、
案内どおり削除すれば pin が全損する」)に照らすと、本件は **`lazyNvim` へのキー追加のみ**で削除は無い。双方向で確認した:

- **新 resolve が旧 plugins.json を `--prev` で読む**: 旧 `lazyNvim` は `{inputName, synthetic, source}` だけ。
  `same_identity`(`:281-302`)は `norm()` を通すので欠けたキーは `nil` として比較され、
  source が一致していれば恒等性が成立して `resolvedRef` は `nil` のまま引き継がれる。正しい。
- **旧 nvimx が新 plugins.json を読む**: `make-env.nix:44` は `inputName` しか読まない。
  `genflake.lua:79` の旧版は `{ source = db.lazyNvim.source }` しか渡さないので、
  ref フィールドを無視して従来どおりの URL を作る(= B に degrade する)。**壊れない**。

### 3.4 `build` / `dependencies` / `lazy = false` / `dev` の扱い

#### `build` — **記録せず、無視することを警告する**

素朴に `classify_build` をそのまま通すと、**誤った案内が出る**。実測(素朴版プロトタイプ、`build = ":TSUpdate"`):

```console
[nvimx] warning: plugin "lazy.nvim": build is a neovim command (":TSUpdate") and cannot be run at build time
[nvimx] these plugins are installed with helptags only, or with some build steps skipped. To give them a real build:
[nvimx]   - programs.nvimx.plugins.overrides."<name>" = { pkgs, src, ... }: <your derivation>;
[nvimx]   - programs.nvimx.plugins.nixpkgsFallback = [ "<name>" ];
...
```

**この案内は lazy.nvim に対しては全部嘘である**。`make-env.nix:47-48` のとおり overrides も nixpkgsFallback も
lazy.nvim には適用されないし、`build-registry` も `resolvedDrvs`(= `pluginsDb.plugins`)にしか効かない。

**採用: lazy.nvim については build 警告も `unbuildable` フラグも出さず、代わりに「無視した」ことだけを 1 行警告する。**
決定は 2 つあり、以降の節はこのラベルで参照する:

- **(i)** 警告の条件は `p.build ~= nil` ではなく `classify_build(p.build).kind ~= "none"` である。
- **(ii)** `unbuildable` フラグ(= `resolve.lua:1286-1293` の escape hatch。`note` が 6 行)も立てない。

**(i) の根拠。**
`extract.lua:98-100` は lazy の "do not build"(`build = false`)を `false` のまま dump し、
`classify_build`(`resolve.lua:483-492`)は `false` と空テーブルの両方を `{ kind = "none" }` に落として何も警告しない。
`p.build ~= nil` で判定すると `{ "folke/lazy.nvim", build = false }` —— **build を明示的に無効化した spec** —— に
「`build` is ignored」という嘘の警告が出て、`plugins.json` の `warnings` にも残ってしまう。
通常プラグイン側の `has_unrunnable`(`resolve.lua:685-686`)が守っている「`none` は黙る」原則に揃える。
`classify_build` は純粋関数で、警告は `build_warning` を呼ぶ側が出しているので、
**判定のために呼ぶこと自体に副作用は無い**(記録しないだけで `entry.build` には入れない)。
**(ii) の根拠。** `unbuildable` を立てると `resolve.lua:1286-1293` の block が発火し、
`:1287-1292` の 6 行の `note` が出る。そこが挙げる 3 つの escape hatch はどれも lazy.nvim には適用されないので、
出せば全部が嘘になる(上の実測がまさにそれである)。実測:

```console
[nvimx] warning: plugin "lazy.nvim": `build` is ignored: nvimx installs lazy.nvim itself, not as a spec plugin
```

`plugin_warnings` 経由なので `plugins.json` の `warnings` にも 1 行入る(golden で固定する。§5.3)。
これは §3.2 の却下 B と同じ原則である: **無視するなら黙って無視しない。**

#### `dependencies` — 記録しない、警告もしない

`dependencies` に挙げられたプラグインは lazy の `Spec.new` が展開して**それぞれ独立した raw.plugins エントリになる**
(§1.5 の実測で `tokyonight.nvim` が別エントリとして出ている)。`lazyNvim` の `dependencies` 配列は
`resolve.lua:334` が明言するとおり参照専用で、**誰も読まない**。落としても失われる挙動は無いので警告しない。
`_comment` と `docs/architecture.md` の schema 節に理由を書く(§5.5)。

#### `lazy = false` / `priority` / `opts` — 何もしない

§1.5 の実測どおり `extract.lua` を通過しない。ランタイムのロード指示であり、
nvimx はユーザーの lua を書き換えない(`docs/architecture.md:121-122`)ので**そのまま効く**。lock 時に扱うものが無い。

#### `dev` / `dir` — **今の挙動を変えない**(スコープ外)

`{ "folke/lazy.nvim", dev = true }` は `resolve.lua:670` の `if p.dev or p.dir` に先に捕まるので、
§3.1 の 3 分岐に到達しない。現行の実測:

```console
$ jq -c '{lazyNvim,localPlugins}' dev.json
{"lazyNvim":{"inputName":"lazy-nvim","source":{...},"synthetic":true},
 "localPlugins":{"lazy.nvim":{"dir":"/home/me/projects/lazy.nvim"}}}
```

`lazyNvim` は synthetic のまま = **衝突しない**ので、#49 の対象外である。
ただし `make-env.nix:109-111` の `devDirs` が `localPlugins` のキーを拾うため、
bootstrap の `dev.path` は lazy.nvim に対して `<devPath>/lazy.nvim` を返す一方、
`bootstrap.lua.in:9` の `vim.opt.rtp:prepend(farm .. "/lazy.nvim")` は farm 固定である。
つまり**実体は store から読まれるのに `:Lazy` は存在しないディレクトリを表示する**。
これは #49 以前から存在する別のバグで、直すには `bootstrap.lua.in` に手を入れる必要がある。
**本件では触らず、§7 に別 issue の候補として残す。** 3 分岐の順序(dev/dir が先)は明示的にそう決めた設計であり、
`flake.nix` のコメントにもそう書く。

### 3.5 `--prev` マージと `pin` 凍結 — `prev.lazyNvim` を読む必要がある

`resolve.lua:175` は `prev_plugins = prev.plugins` だけを読む。したがって統合しただけでは
`prev_plugins["lazy.nvim"]` が常に `nil` になり、**マージ契約も pin 凍結も一切効かない**。実測(この手当て前のプロトタイプ):

```console
--- pass1 (no prev) ---   {"pin":true,"resolvedRef":null,...}
--- pass2 (prev=pass1) --- {"pin":true,"resolvedRef":null,...}   ← 凍結されない
```

**採用: `--prev` を読むときに `prev_plugins["lazy.nvim"] = prev.lazyNvim` を注入する。**
`lazy_entry` が `plugins` ではなく `lazyNvim` に出て行くのと対称の、1 行の入り口側の手当てである。実測(手当て後):

```console
--- pass1 (no prev) ---
{"branch":null,"commit":null,"inputName":"lazy-nvim","pin":true,"resolvedRef":null,"source":{...},"synthetic":false,"tag":null,"version":null}
--- pass2 (prev=pass1) ---
{"branch":null,"commit":null,"inputName":"lazy-nvim","pin":true,"resolvedRef":"eeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee","source":{...},"synthetic":false,"tag":null,"version":null}
$ nvim -l genflake.lua pin2.json pin2.flake.nix && head -8 pin2.flake.nix
...
    lazy-nvim = {
      url = "github:folke/lazy.nvim/eeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee";
--- pass3 (idempotent) ---
converged
```

`eeee…` は `tests/fixtures/merge/flake.lock` の `lazy-nvim` ノードが持つ rev である。
`locked_rev(input_name)`(`resolve.lua:250-259`)は `inputName` で引くので、`lazy-nvim` は**そのまま引ける**。
**`lock-app.nix:279-293` の 2 パス収束がそのまま働き、3 パス目は byte 一致する**(実測 `converged`)。
新しい収束パスも新しい条件分岐も要らない。

`prev_plugins` への注入は 2 つの副作用を持つが、どちらも望ましい方向である:

- `--import-lazy-lock` の seed ガード(`resolve.lua:762` の `not (prev_plugins and prev_plugins[name] ~= nil)`)が
  lazy.nvim にも効く = 既存 lock の決定が import に勝つ。他プラグインと同じ規則。
- `resolve.lua:1099-1105` の `lazy_self` 分岐(classification 8)は `raw_plugins[n] == nil` のときだけ通るので、
  spec が lazy.nvim を書いている場合は**普通の matched plugin として seed される**。§3.8。

### 3.6 `--update lazy.nvim` — `force` を立てないと再解決されない

`resolve.lua:635-638` は `--update lazy.nvim` を受理して `lazy_requested = true` にするだけで、
`force[name]` を立てない(当時は spec プラグインではあり得なかったので正しかった)。統合後はこれが穴になる。実測:

```console
$ # prev の lazyNvim.resolvedRef == "refs/tags/v11.14.1"、remote に v11.14.9 を追加済み
$ nvim -l resolve.lua raw-version.json v3.json --prev ver.json --lazy $seed --update lazy.nvim --update-plan plan3.txt
$ jq -r .lazyNvim.resolvedRef v3.json
refs/tags/v11.14.1        ← 動いていない
```

**採用: `name == "lazy.nvim"` かつ **spec の lazy.nvim が統合対象であるとき**は `force[name] = true` も立てる。** 実測(手当て後):

```console
nvimx-lock: resolving version constraints for 1 plugin(s)
$ jq -r .lazyNvim.resolvedRef v4.json
refs/tags/v11.14.9
$ cat plan4.txt
lazy-nvim
```

#### 「統合対象である」の述語 — `dev`/`dir` を必ず除外する

§3.4 のとおり `dev`/`dir` な lazy.nvim は `local_plugins` へ行き、`lazyNvim` は synthetic のままである。
本節の 2 つの条件はどちらもその除外を含まなければならない。**共通の述語を 1 つ用意する**:

```lua
local lp = (raw.plugins or {})[LAZY_NAME]
local lazy_is_spec = lp ~= nil and not (lp.dev or lp.dir)
local lazy_pinned = lazy_is_spec and is_true(lp.pin)
```

除外しないと 2 つ壊れる:

- **`force` 側**: `{ "folke/lazy.nvim", dev = true }` に `--update lazy.nvim` を渡すと `force` が立つ。
  通常のローカルプラグインは `resolve.lua:648-649` の
  `fail_plugin(name, "is a local plugin (dev/dir); nothing to lock or update")` で fatal になるのに、
  lazy.nvim だけ黙って受理される。実害は小さいが、本節が下で述べる「lazy.nvim だけ規則が違う状態を残さない」(および §4.3.1 の同じ原則)に反する。
  (ただし本件では **fatal にはしない**: `--update lazy.nvim` は `dev` の有無に関わらず
  「合成 seed input を動かす」という #24 からの正当な意味を持ち続けるので、
  `lazy_requested` は今までどおり立てて `force` だけ立てない、が正しい。)
- **update-plan 側(こちらが実害)**: `{ "folke/lazy.nvim", dev = true, pin = true }` で `lazy_pinned` が真になり、
  下記の `(update_all and not lazy_pinned)` により **素の `--update` が合成 `lazy-nvim` seed input を更新しなくなる**。
  このとき `lazyNvim` は synthetic で、尊重すべき `pin` はそもそも存在しない。
  `docs/architecture.md:274` の #24 の契約を破る。
  なお `resolve.lua:660-666`(全体更新の force 集合)は `not (p.dev or p.dir)` を既に持っているので、
  **この非対称は plan writer 側にだけ生じる**。

`--update`(全体)側は `resolve.lua:660-666` が `raw.plugins` を舐めて `force` を立てるので**既にカバーされている**。
update-plan の重複も起きない: `:1318-1322` の `for name, entry in pairs(plugins)` は
lazy.nvim を含まなくなり、`lazy-nvim` は `:1323-1325` の `update_all or lazy_requested` 分岐からのみ 1 回入る。実測:

```console
$ cat plana.txt   # --update (全体)
lazy-nvim
tokyonight-nvim
```

#### `update_all` × `pin = true` の非対称を潰す

ただし全体更新の 2 つの経路は `pin` の扱いが揃っていない:

- `resolve.lua:660-666`(force 集合)は `not is_true(p.pin)` を条件にするので、
  **`pin = true` の lazy.nvim には `force` が立たない**(= `resolvedRef` は捨てられない)。正しい。
- `resolve.lua:1323-1325`(update-plan writer)は `update_all` なら**無条件に** `lazy-nvim` を plan に足す。
  結果として `lock-app.nix:247-253` が `nix flake update lazy-nvim` を走らせる。

通常プラグインは `pin = true` なら plan に入らないのに、lazy.nvim だけ入る。実害は限定的である
(凍結済みなら input URL が rev を名指しするので `nix flake update` は動かせない)が、
**これは §4.3 の finding と同根の「lazy.nvim だけ規則が違う」**であり、
統合後は `pin` が spec から来る本物の意図になるので放置しない。

**採用: 上の `lazy_pinned`(= 統合対象 **かつ** `pin` が真)のときは `update_all` でも plan に `lazy-nvim` を足さない。**
すなわち plan の条件を `(update_all and not lazy_pinned) or lazy_requested` にする。

- **`raw.plugins` に lazy.nvim が居ない、または `dev`/`dir` のとき(= `lazy_is_spec` が偽)は無条件のままにする。**
  どちらの場合も `lazyNvim` は synthetic で、尊重すべき `pin` がそもそも存在せず、
  「no-names update は lazy.nvim を自動的に含める」は `docs/architecture.md:274` が明文化した #24 の契約だからである。
- **`--update lazy.nvim` と名前で指定した場合は `pin` があっても plan に入れる。** 通常プラグインの
  「名前を明示した = pin を上書きする意図」(`resolve.lua:651-653` のコメント)と同じ規則である。

### 3.7 semver ゲート — `docs/plans/23-resolve-semver.md:235` の申し送りへの回答

§3.7 の申し送りは「統合の仕方によっては `version` 制約が黙って捨てられる」を懸念していた。
**採用した C ではゲートは発火する。** `resolve.lua:801-818` のゲートは `p.version`(raw 側)を見て
`pending` に `{ name, entry, url, constraint }` を積み、`:970` が `item.entry.resolvedRef` に**参照で**書き戻す。
`lazy_entry` は同じ Lua テーブルなので、行き先を変えても解決結果はそこに入る。

github type は remote を差し替えられない(`resolve.lua:812` が `p.url` をそのまま ls-remote に渡す。
`docs/plans/29-genflake-golden.md:320-326` と同じ制約)ので、**git type の lazy.nvim フォーク**で hermetic に実測した
(`mkTagRepoSh` 相当のローカル repo。タグ `v11.0.0 v11.14.0 v11.14.1 v12.0.0` の **4 本**、制約 `^11.14`):

```console
$ nvim -l resolve.lua raw-version.json ver.json --lazy $seed
nvimx-lock: resolving version constraints for 1 plugin(s)
$ jq -c .lazyNvim ver.json
{"branch":null,"commit":null,"inputName":"lazy-nvim","pin":null,"resolvedRef":"refs/tags/v11.14.1",
 "source":{"type":"git","url":"file:///.../repo/lazy"},"synthetic":false,"tag":null,"version":"^11.14"}
$ nvim -l genflake.lua ver.json ver.flake.nix && head -6 ver.flake.nix
...
    lazy-nvim = {
      url = "git+file:///.../repo/lazy?ref=refs/tags/v11.14.1";
```

- ゲートは発火し、制約は捨てられない。
- `v12.0.0` が範囲外として正しく負ける。
- `genflake.lua` の **git type 分岐が `lazyNvim` スロットに対して初めて走る**
  (従来この行が作れる URL は `github:folke/lazy.nvim` だけだった)。
- 続けて `--prev` を渡した素の再 lock では `refs/tags/v11.14.1` が引き継がれ、ls-remote は走らない(実測)。
  マージ契約が他プラグインとまったく同じに効いている。

**タグは 4 本で始めなければならない。** `lua/nvimx/version.lua:81-84` の `select_tag` は
範囲に合致したもののうち **`Semver.last(matched)` = 最新**を返す:

```lua
  if #matched > 0 then
    local winner = Semver.last(matched)
    return winner.input, nil
  end
```

したがって repo に最初から `v11.14.9` があると `^11.14` は 1 回目から `v11.14.9` に解決され、
`refs/tags/v11.14.1` を assert する余地が無くなる。§3.6 の `--update` 実測が
「remote に `v11.14.9` を**追加済み**」と書いているのは、**2 つの resolve のあいだで 5 本目を打った**という意味である。
check もその順序を再現する(§5.4 / §6.1 のステップ 3)。

**したがって §3.7 の申し送りは「発火する。統合の形は C」で discharge される。**
`resolve.lua` の該当箇所に `#49` と `#23 §3.7` を名指しするコメントを置く(§5.1)。

github type + `version`(= `{ "folke/lazy.nvim", version = "*" }` そのもの)は
**lock 時に github.com へ実際に ls-remote する**。lock はもともと唯一のオンライン工程なので設計上問題無いが、
check ではオフライン維持のため扱えない。この非対称は #28 の follow-up 領域であり本件では扱わない(§7)。

### 3.8 `--import-lazy-lock` との相互作用

`resolve.lua:1099-1105` のコメントは事実として**誤っている**:

> nvimx pins lazy.nvim through its own synthetic flake input, never through a config plugin entry

§1.1 の実測で `raw.plugins` に `lazy.nvim` キーが入ることが確認できている。**#49 以前から誤っていた記述**である。

後者は**望ましい**: 「今動いている lazy.nvim の commit で止めたい」がまさに `--import-lazy-lock` の目的であり、

**ただしこれは挙動変更であり、check が要る。** #25 は "lazy.nvim itself is not imported" を

seed は lazy-lock.json の `commit` を `resolvedRef` に書くだけで ls-remote を必要としないので、**完全にオフラインで覆える**。

### 3.9 予約名との衝突の検出 — 決定的な報告に作り直す

§1.3 後者(`lazy.nvim` ではないが input 名が `lazy-nvim` になるプラグイン)を fatal にする。
§1.6 で見たとおり、既存の検査を素朴に拡張すると非決定性を新しい check に持ち込むので、
**2 種類の衝突を別々に扱う**:

```lua
-- ループ前。lazy.nvim 自身が予約名を「すでに主張している」状態を作る
seen_inputs[LAZY_INPUT_NAME] = LAZY_NAME
```

**この検査全体が `not is_lazy` のガードの内側にある**(§3.1)。`to_input_name("lazy.nvim")` は
`lazy-nvim` を返すので、ガードが無いと**予約シードが lazy.nvim 自身を弾く** — 案 C の
メインケースがそのまま fatal になる。以下の 2 分岐はどちらも `name ~= LAZY_NAME` が前提である:

- **予約名との衝突**(`name ~= LAZY_NAME and claimed == LAZY_NAME`): 主張している側は
  シードによって常に `lazy.nvim` で固定なので、その場で `fail_plugin(name, ...)` して良い。決定的。
  `seen_inputs` は**上書きしない**ので、`lazy-nvim` に落ちるプラグインが 2 つあれば 2 件とも同じ文言で報告される。
- **プラグイン同士の衝突**(`name ~= LAZY_NAME and claimed` が別のプラグイン名): どちらが「先」かは
  `pairs()` 次第なので、`collisions[input_name]` に**全員**を集め、ループ後に input 名でソート →
  プラグイン名でソートして 1 件ずつ報告する。

実測(6 回連続、`{lazy-nvim, foo.nvim, foo-nvim, tokyonight.nvim}` を含む raw-spec):

```console
      6 [nvimx] resolve failed: plugin "foo-nvim": flake input name "foo-nvim" is derived from more than one plugin (foo-nvim, foo.nvim); give all but one of them a different `name` in the spec
      6 [nvimx] resolve failed: plugin "lazy-nvim": flake input name "lazy-nvim" is reserved for lazy.nvim itself; give this plugin a different `name` in the spec
rc=1
```

6/6 で完全に同一。素朴版が 8 回中 1 回文言を変えていた(§1.6)のと対照的である。

設計上の決定:

1. **`error()` ではなく `fail_plugin` を使う。** #28 が確立した「per-plugin fatal は集めて一度に、名前順で報告し、
   `plugins.json` は 1 バイトも書かない」に揃える(`resolve.lua:376-390` の `report_resolve_errors`)。
   issue が求めた `[nvimx] ...` 経路はこれである。実測で `plugins.json` が作られないことも確認済み。
2. **既存の衝突検査も同時に載せ替える**(`resolve.lua:674-677` の `error()` を置き換える)。
   合成エントリを同じテーブルに参加させる以上、片方だけ経路が違う状態を残す方が不整合である。
   副産物として §1.6 の非決定性バグも消える。
3. **助言は実行可能にする**: lazy spec は `name = "..."` を受け付けるので、
   「`name` を変えろ」は実際に踏める手順である(`{ "someone/lazy-nvim", name = "someones-lazy" }`)。
4. **衝突したプラグインは `plugins` に入れない**(`seen_inputs` を上書きしないので 2 件目以降も同じ相手と衝突する)。
   ただしループ自体は続ける — #28 の `source_ok` と同じで、1 回の lock ですべての問題を報告するためである。
   **実装形は `local collided` フラグであって反復の早期スキップではない**(§5.1 (d)):
   飛ばすのは `resolve.lua:824` の `plugins[name] = entry` の 1 行だけで、
   entry の組み立てから semver ゲートまでは必ず通す。スキップにすると下のゲート条件が死にコードになり、
   摂動 (o) が実行不能になる。
   その代わり semver ゲート(`:801`)の条件に「衝突していない」を加え、**すでに詰んでいる run に ls-remote を使わせない**。
   動機は `resolve.lua:812-818` のコメントが `source_ok` について書いているものと同じである。

   **抑止の強度は 2 つの衝突種で違う。**

   - **予約名側は完全に決定的である。** claimant はループ前のシードによって常に `lazy.nvim` に固定されており、
     victim(`someone/lazy-nvim` など)が `:801` に到達する前に必ず衝突が判明している。
     **したがってここは check で守れる**(§6.3 (o))。
   - **プラグイン同士の側は片側にしか効かない。** `collisions` に積まれるのは
     **後から検出された側**だけで、先に `seen_inputs` に入った claimant の entry は
     衝突が判明する前に `:801` を通過しており、すでに `pending` に入り得る。
     どちらが claimant になるかは `pairs()` 順なので、こちらは
     **1/2 の確率でしか成立しない**非決定的な性質である。
     claimant まで外すには「衝突を全部集めてからゲートを回す」2 パス構成が要るが、
     **本件ではやらない**: 実害は「詰んでいる run が ls-remote を 1 本余計に撃つ」だけで
     (`report_resolve_errors()` がどのみち `plugins.json` を書かせずに落とす)、
     2 パス化はメインループの構造変更という不釣り合いなコストを伴う。
     **この側は check で assert しない**(§7)。

   `source_ok`(プラグイン単位で決定的)と同型なのは**予約名側だけ**である、という区別をコメントに明記する。

## 4. 既存機能との関係

### 4.1 #32(`fix(lock): use the locked lazy.nvim as the extraction seed`)

#32 は `nix/lib/lock-app.nix:124-126` の TODO を潰す issue である:

```bash
    # TODO: if the existing lock pins lazy.nvim, use that as the seed (to avoid skew).
    # For now nvimx's own flake input is always used as the seed.
    seed="${lazyNvimSeed}"
```

**本件は #32 を実装しない。** 実装すると lock-app が `lockDir/flake.lock` から store path を取り出す
(= スクリプト内で `nix build` / `nix eval` を走らせる)必要があり、それが #32 の設計面のすべてだからである。
問うべきは「#32 が後から素直に載るか」であり、以下 4 点で**載る**と判断した。

1. **#32 の読み口が 1 つのままである。** #32 は「lock が lazy.nvim を pin しているか」を見る。
   その所在は `plugins.json` の `lazyNvim.inputName` → `flake.lock` の `nodes[root.inputs["lazy-nvim"]].locked` であり、
   **これは `nix/lib/sources.nix:9-21` が既にやっている経路そのもの**である。
   本件は input 名(`lazy-nvim`)も、lazy.nvim の source が `plugins.json` の中で 1 箇所にしかないことも変えない。
   §3.2 で却下 D(リネーム)を退けた理由の 1 つがこれである。D を採ると #32 は
   「`lazyNvim` か `plugins["lazy.nvim"]` か」の選択から設計を始めることになり、
   §1.4 のとおり後者は farm を壊すので、結局この形に戻ってくる。

2. **#32 の判定材料が増える。** `lazyNvim.synthetic` が `false` なら「ユーザーが明示的に決めた lazy.nvim」であり、
   #32 が「skew を避けるために lock 側を使う」べき度合いが最も高いケースである。
   `synthetic` は現在誰も読まないフィールドだが、#32 が最初の読み手になれる(§3.3 でこのキーを残した理由)。
   ただし **#32 が `synthetic` を読むことを前提にはしない**: `synthetic == true` の場合も
   lock の `lazy-nvim` ノードは実在するので、#32 の「lock があればそれを使う」は
   `synthetic` の値に関係なく成立する。本件はあくまで材料を増やすだけである。

3. **#32 の必要性を上げるが、新しい skew は作らない。** skew は**今日すでにある**:
   nvimx 自身の `flake.lock` の `lazy-nvim`(rev `306a055`)と、ユーザーの lockDir の `lazy-nvim`
   (`github:folke/lazy.nvim` を各自の lock 時刻に pin したもの)は**別々に動く 2 つの pin** であり、
   一致するのは偶然にすぎない(本リポジトリの `tests/fixtures/basic-config/nvimx-lock/flake.lock` が
   たまたま `306a055` なのは、fixture を同時期に生成したからである)。
   `docs/plans/24-lock-update.md:829-833` も `--update` で skew が顕在化しやすくなることを既に記録している。
   本件が変えるのは「skew が**偶然**から**ユーザーの選択**に変わる」点である
   (v11.14.1 に pin したユーザーの抽出は #32 が入るまで nvimx 側の新しい lazy.nvim で走る)。
   **これは #49 の優先度上げではなく #32 の優先度上げとして扱う**(§7)。

4. **#32 の収束性は本件の後でも壊れない。** #32 実装後の連鎖は
   「seed = 前回 lock の lazy.nvim → extract → raw-spec に `tag = v11.14.1` → lock がそれを pin」である。
   spec の tag を書き換えた直後の 1 回だけ「seed は古い lazy.nvim、pin は新しい tag」になるが、
   **pin 自体はその回で即座に効く**(seed が決めるのは名前導出規則だけである)。
   次の lock で seed も追いつき、以降は不動点。1 回分のラグは #32 が扱うべき性質であって、
   本件が持ち込む障害物ではない。

**#32 側への申し送り**(#32 の計画書に書くべきこと): `synthetic == false` の lock を seed に使うと、
「ユーザーが指定した lazy.nvim で spec を正規化する」ことになり、これは #32 の目的
(`docs/architecture.md:223` の "preventing version skew in the name derivation rules")に完全に合致する。
逆に `synthetic == true` でも lock の rev を使うべきである(理由は上記 2)。

#### 4.3.1 `update-summary.lua` は 3 点壊れる — 直す

`lua/nvimx/update-summary.lua:291-310` の lazy.nvim 専用分岐は `lazy_moved`(rev が動いたか)しか見ない。
統合すると、**通常プラグインなら当たり前に得られる 3 つの挙動が lazy.nvim だけ得られない**:

| # | 症状 | 通常プラグインなら |
|---|---|---|
| (a) | `pin = true` の lazy.nvim が `pinned: lazy.nvim (skipped; run ...)` として報告されず、`unchanged: lazy.nvim (seed)` になる | `classify()`(`:190-288`)の `kind = "pinned"` 分岐(`:214-219`)。#24 が意図的に用意した表示 |
| (b) | spec 編集による正当な移動が「名前指定なしで動いた」の**誤検知**になる。`--update tokyonight.nvim` と同時に spec の lazy.nvim の `tag` を変えると rev は動くが、理由を判定する経路が無いので `warning: 1 input(s) moved without being named: lazy.nvim` が出る | `same_identity` → `reason = "spec changed"` → `explained` → 警告なし(`:259-262`) |
| (c) | 出力ラベルが `lazy.nvim (seed)` のままで、spec プラグインになった場合に不正確 | 名前そのまま |

**(b) が決定的である。** これは `--update` の安全網(`docs/architecture.md:274` の
"warns if an unnamed input moved for no reason the summary can account for")に対する**偽陽性**であり、
安全網の信頼性そのものを損なう。しかもこの非対称は `flake.nix:2400-2405` のコメント
*"lazy.nvim has no plugins.json entry to check a reason against"* が**明文で前提にしている**もので、
本件はまさにその前提を崩す。放置すると check のコメントが嘘になる。

**採用: `synthetic == false` の `lazyNvim` を `plugins_before` / `plugins_after` に注入し、`classify()` に通す。**
これは §3.5 で `resolve.lua` の `prev_plugins` に対してやるのと**まったく同型の入り口側の手当て**である
(書き出し側で `lazyNvim` に出て行くものを、読み込み側で `plugins` に戻す)。

```lua
-- update-summary.lua:139-140 付近、plugins_before / plugins_after を作った直後
local lazy_is_spec = <before または after の lazyNvim.synthetic == false>
if lazy_is_spec then
  plugins_before[LAZY_NAME] = plugins_before_doc.lazyNvim
  plugins_after[LAZY_NAME] = plugins_after_doc.lazyNvim
end
```

これだけで `all_names`(`:166-179`)が `lazy.nvim` を拾い、`classify()` が `inputName`(= `lazy-nvim`)から
rev を引き、`added` / `removed` / `pinned` / `spec changed` / `unpinned` を**すべて通常プラグインと同じ規則で**判定する。
必要な追加の手当ては 2 つだけ:

1. **`--update lazy.nvim` を `requested_set` に入れる**(`:154-162`)。現在は `lazy_requested` という別変数に振り分けられており、
   `classify()` は `requested_set[name]` しか見ない。`lazy_is_spec` のときは通常の名前として扱う。
2. **`:291-310` の専用 seed 分岐を `lazy_is_spec` のときスキップする**。しないと lazy.nvim が 2 行報告される。
   `lazy_is_spec` が偽(= 従来どおり synthetic)のときは**この分岐がそのまま生き、出力は 1 バイトも変わらない**。

混在ケースも正しく落ちる。before が synthetic で after が非 synthetic(ユーザーが lazy.nvim の行を足した直後)なら、
`lazy_is_spec` は真、注入された before エントリは ref フィールドを持たないので `same_identity` が偽 →
`reason = "spec changed"` → 警告なし。逆(行を消した)も同じ。
`rb` / `ra` はどちらも非 nil(`lazy-nvim` ノードは常に lock に居る)なので `added` / `removed` にはならない。

**argv の指定は (a) と (b) で逆でなければならない。** `update-summary.lua:280` の include 規則は

```lua
    local include = mode_all or c.kind == "added" or c.kind == "removed" or c.kind == "updated" or requested_set[name]
```

なので、`kind == "pinned"` の行が出力に載るのは **`mode_all`(名前を 1 つも渡していない)か
`requested_set[name]` が真のとき**に限られる。(a) は名前を渡さない素の `--update` にしないと
`pinned: lazy.nvim (skipped` が**そもそも印字されず** assert が落ちる。
逆に (b) は「名前指定モードなのに指定外の input が動いた」という安全網の話なので、名前指定が必須である。

**(b) に渡す名前は `lazy.nvim` 以外でなければならない。** `lazy.nvim` を渡すと `lazy_requested` が真になり、
注入を消したときに `update-summary.lua:303` の `not mode_all and not lazy_requested` が偽になって
`warn_names` に積まれない。つまり摂動 (g) で落ちるのが `grep -q 'spec changed'` の片方だけになり、
**(b) の本来の主張(安全網の誤検知を防ぐ)が検証されない**。
`lazy.nvim` 以外を渡せば、注入を消したときに `:297-310` の専用分岐が生きて
「`spec changed` が出ない」と「`moved without being named` が出る」の**両方**が落ちる。
`update-summary.lua:32-35` は argv の名前を検証しないので、**fixture の `plugins` に存在しない名前でよい**
(`tokyonight.nvim` を使う。`summary-*.plugins.json` の `plugins` は空でよい)。

**check**: `checks.update-summary` に 1 ケース足す(§5.4)。既存の 3 本の golden
(`update/golden/summary-{all,named,none}.txt`)を動かさないために、**既存 fixture は 1 バイトも編集せず**、
`tests/fixtures/lazy-self/` に summary 用の plugins.json 2 本を新設して既存の lock 2 本を再利用する(§5.3)。
`checks.resolve-update` が `merge/` の fixture を参照している(`flake.nix:2150-2160` の `$mfx`)のと同じ、

## 5. 実装手順

### 5.1 `lua/nvimx/resolve.lua`

§3.10 の表のとおり。コメントに必ず含めること:

- `LAZY_NAME` / `LAZY_INPUT_NAME` の宣言箇所に、**なぜ lazy.nvim が `plugins` に入れないのか**
  (`make-env.nix:122-133` の farm が `lazy.nvim` を無条件に 1 件置き、`linkFarm` が last-wins なので
  2 件目が黙って foundation を置き換える。`make-env.nix:47-48` と `docs/architecture.md:345` が禁じている状態になる)。
- **`is_lazy` の判定が衝突検査より前に来ている理由**(§3.1)。`to_input_name("lazy.nvim") == "lazy-nvim"` なので、
  予約シードを置いたうえで `not is_lazy` のガードを外すと**案 C のメインケースが自分で自分を弾く**。
  この 1 行が消えたときに何が起きるかを、コメントで名指ししておく(§6.3 (e'))。
- 3 分岐の**順序**が意図的であること(`dev`/`dir` が先。§3.4 の理由と、それが #49 の対象外であること)。
- `prev.lazyNvim` の注入(§3.5)に、これが無いと pin 凍結もマージ契約も一切効かないこと
  (実測で pass2 が `resolvedRef: null` のままだったこと)。
- `--update lazy.nvim` の `force`(§3.6)に、`raw.plugins` に居るときだけ立てること
  (居ないときは update-plan エントリだけ = `:635-638` の従来挙動)。
  **`:636-637` のコメント *"Accepted, but it is not a spec plugin: ... never a `force` entry"* も同時に訂正する**:
  統合後は「spec が lazy.nvim を書いていない場合に限り真」である。
- update-plan writer(`:1323-1325`)の `not lazy_pinned`(§3.6)に、通常プラグインが `pin = true` で
  plan に入らないのと揃えたこと、および spec に lazy.nvim が居ないときは無条件のままにする理由
  (`docs/architecture.md:274` の #24 の契約)。
- `build` を捨てる理由(§3.4)に、`classify_build` の警告が指す 3 つの escape hatch が
  lazy.nvim には 1 つも適用されないこと。**判定が `kind ~= "none"` である理由**(`build = false` は
  lazy の "do not build" であり、そこに「ignored」と言うのは嘘になる)。
- 衝突検出(§3.9)に、`fail_plugin` を選んだ理由と、**プラグイン同士の衝突だけ収集が要る理由**
  (`pairs()` 順で「先に見つかった側」が変わるので、その場で報告すると 8 回に 1 回文言が変わる。実測)。

衝突収集は 3 段階ある。素直に「後から来た側だけを `collisions` に足す」と実測メッセージの
`(foo-nvim, foo.nvim)` という**両方の名前**が作れないので、擬似コードで示しておく:

```lua
-- ループ内(§3.1 の `not is_lazy` ガードの中)
local collided = false                   -- (d) フラグにする。ここで反復を打ち切らない
local claimed = seen_inputs[input_name]
if claimed == LAZY_NAME then
  -- 予約名。claimant はシードで固定なので決定的。その場で報告してよい
  fail_plugin(name, ("flake input name %q is reserved for lazy.nvim itself; ..."):format(input_name))
  collided = true
elseif claimed then
  -- (a) claimant も一緒に入れる。初回だけ { claimed } で作るのがその役割で、
  --     これを忘れると報告に名前が 1 つしか並ばない
  collisions[input_name] = collisions[input_name] or { claimed }
  local c = collisions[input_name]
  c[#c + 1] = name
  -- seen_inputs は上書きしない。3 つ目が来ても claimant は同じ 1 人のままで、
  -- 同じリストに積み上がる
  collided = true
else
  seen_inputs[input_name] = name
end

-- ここから下(entry の組み立て / merge / pin 凍結 / import seed / semver ゲート)は
-- 衝突していても **そのまま全部通す**。飛ばすのは最後の 1 行だけ:
--   if not collided then plugins[name] = entry end
-- semver ゲート(:801)の条件に `not collided` を足す(§3.9-4)

-- ループ後
local input_names = <collisions のキーをソート>
for _, n in ipairs(input_names) do
  local names = collisions[n]
  table.sort(names)                      -- (b) 名前をソートし、
  fail_plugin(names[1], (                --     先頭を fail_plugin のキーにする
    "flake input name %q is derived from more than one plugin (%s); ..."
  ):format(n, table.concat(names, ", ")))
end
```

- **(a)** `collisions[input_name] or { claimed }` の `{ claimed }` が、`seen_inputs` に先に入った側を
  リストに引き込む唯一の場所である。
- **(b)** `table.sort(names)` の結果の**先頭**を `fail_plugin` の `name` に渡す。
  `pairs()` 順に依存しない選び方はこれだけで、メッセージ本文の `(foo-nvim, foo.nvim)` も同じソート結果である。
- **(d)** **`collided` は「フラグ」であって「早期スキップ」ではない。**
  「衝突したプラグインは `plugins` に入れない」を `goto continue` 相当の反復スキップとして実装すると、
  そのプラグインは `resolve.lua:801` に**到達しなくなり**、ゲートに足した `not collided` が死にコードになる。
  そのとき**ステップ 4 は 2 行のまま緑で通る**のに §8-6 で摂動 (o) を打っても落ちず、
  原因を追う手掛かりがどこにも無い状態になる。
  precedent の `source_ok`(#28)も同じで、**URL を拒否されたプラグインは反復をスキップせず
  `resolve.lua:693-824` を最後まで通り、`:824` の `plugins[name] = entry` もそのまま実行する**
  (`plugins.json` が書かれないのは `report_resolve_errors()` が先に落とすからであって、
  エントリを作らないからではない)。`collided` が `source_ok` と「同じ」なのはこの点である。
  飛ばしてよいのは `plugins[name] = entry` の 1 行だけで、そこだけは
  `plugins` に衝突する `inputName` を 2 つ入れないために飛ばす。
- **(c)** 最終的な行の並びは `report_resolve_errors`(`resolve.lua:376-390`)の
  `table.sort(resolve_errors, ...)` が決める。したがって予約名の枝(その場で `fail_plugin`)と
  収集の枝(ループ後に `fail_plugin`)が**呼ばれる順序は出力順に影響しない** —— §6.1 ステップ 4 の
  `LC_ALL=C sort -c` はそのことを assert している。
- semver ゲート(`:801`)に「衝突している plugin は queue しない」を足した理由が `source_ok` と同型であること。
- `:1099-1105` のコメント訂正(§3.8)。旧文の *"raw.plugins has no 'lazy.nvim' key at all -- extract.lua never adds one"* は
  誤りで、spec が書けば入る。分岐の条件(`raw_plugins[n] == nil`)は変えないので**挙動は変わらない**ことを明記する。

**`lua/nvimx/` は stylua / luacheck の対象**(#31)なので、`nix fmt -- --ci` を通すこと。

### 5.4 `flake.nix` — 新 check 1 本 + 既存 check 2 本へのケース追加 + コメント訂正 2 箇所

**挿入位置**: `checks.genflake-golden` は `flake.nix:2998` の `'';` で終わり、`:2999` から
`dev-plugins` の説明コメントが始まる。**`:2999` の直前**に挿入する
(#29 が `resolve-sources` の直後に 2 本入れたのと同じ位置取り。`resolve-*` 系がファイル後半に固まる並びを保つ)。

構造は #28 / #29 に倣う。**evaluation 時のガードが本件では特別な意味を持つ**:

```nix
          # The lazyNvim slot itself (#49). A spec is allowed to list lazy.nvim -- lazy's own docs
          # tell people to -- and it used to make genflake write `inputs.lazy-nvim` twice, so the
          # generated flake died at `nix flake lock` with a duplicate-attribute error naming
          # neither the plugin nor the spec line. lazy.nvim cannot become an ordinary plugin
          # instead: make-env.nix's farm always puts one `lazy.nvim` entry in front of pluginDrvs,
          # and linkFarm is last-wins, so a second entry would silently replace nvimx's own
          # foundation -- exactly what make-env.nix:47-48 says never happens. So the spec entry
          # decides the *existing* input instead, and this check owns that slot. The spec-field
          # matrix on ordinary plugins is checks.resolve-golden's (#29), the input_url precedence
          # ladder is checks.genflake-golden's, and URL shapes are checks.resolve-sources' (#28);
          # none of the three ever sees lazyNvim carrying a ref.
          resolve-lazy-self =
            let
              # Importing the golden flake IS the regression test for the original bug: a
              # duplicate attribute is a *parse* error in Nix, so a golden that reintroduced the
              # second `lazy-nvim` would fail here, at evaluation, before any builder runs -- and
              # `nix eval .#checks.aarch64-darwin.resolve-lazy-self.drvPath` catches it on a
              # system this machine cannot build for. The diff in the builder is what proves
              # genflake still produces exactly this file. The parseFlakeRef type assert is the
              # same one checks.resolve-sources and checks.genflake-golden use (#28/#29): a github
              # or git ref, never a degraded `path:` / `indirect` node that only dies later in
              # nix/lib/sources.nix.
              goldenFlake = import ./tests/fixtures/lazy-self/golden/tag.flake.nix;
              refTypes = builtins.mapAttrs (_: i: (builtins.parseFlakeRef i.url).type) goldenFlake.inputs;
              badTypes = pkgs.lib.filterAttrs (_: t: t != "github" && t != "git") refTypes;
              checkedRefTypes =
                if badTypes == { } then
                  refTypes
                else
                  throw "generated flake inputs are not github/git refs: ${builtins.toJSON badTypes}";
            in
            pkgs.runCommand "resolve-lazy-self"
              {
                nativeBuildInputs = [
                  pkgs.neovim-unwrapped
                  pkgs.jq
                  pkgs.git
                ];
                refTypes = builtins.toJSON checkedRefTypes;
              }
              (mkTagRepoSh + '' ... '');
```

builder の前置きは `checks.resolve-golden`(`flake.nix:2880-2884`)と同じ 5 行にする。
本節の bash 断片はすべてこの束縛を前提にしている:

```bash
export HOME=$TMPDIR
lua=${./lua/nvimx}
fx=${./tests/fixtures/lazy-self}
lazy=${lazy-nvim}
sb=$TMPDIR/sandbox
```

`export HOME=$TMPDIR` は `mkTagRepoSh` の既存 4 利用者(`flake.nix:1379-1380`、`:1888-1892`、
`:2119-2124`、`:2880-2884`)がすべて置いている。git 自体は `HOME` 不在でも動くが、
`nvim -l` を含めて全 check が揃えている以上ここも揃える。

ステップは 5 つ(ステップ 3 は 3a / 3b / 3c の 3 段、ステップ 5 は 5a / 5b の 2 fixture。内容は §6.1 の表)。
コメントに必ず入れること:


- **(1) tag**: golden 2 本の `diff -u`。`grep -c 'lazy-nvim = {'` が 1 であること — これが
  「duplicate が消えた」の直接の表明で、`diff -u` が落ちたときにどちらの意味で落ちたかを読み手に伝える。
  `[ "$(grep -c ...)" -eq 1 ]` は**単純コマンド**なので `|| true` は要らない
  (`checks.resolve-golden` のコメント `flake.nix:2913-2919` が説明している罠は単独の代入文の方である)。
  警告がちょうど 1 件で、それが `build` の無視であること。

  **加えて stderr が「その 1 行だけ」であること** —— `[ "$(wc -l < resolve.log)" -eq 1 ]` と
  `! grep -q 'programs.nvimx.plugins.overrides' resolve.log`。これが §3.4 (ii)
  (`unbuildable` を立てない)の唯一のガードである。escape hatch の 6 行は
  `note()`(`resolve.lua:357-359`)なので `[nvimx] ` 止まりで **`warning: ` を含まず**、
  上の「警告ちょうど 1 件」のカウント(`grep -c '^\[nvimx\] warning: '`)には 1 件も乗らない。
  golden も stderr を見ない。**総行数で見なければ `unbuildable = true` を残した実装が素通りする**。
  `! grep -q` の方は落ちたときにどの 6 行かを名指しするために添える。
- **(2) pin**: `--lock` 付き 2 パス。1 パス目は `resolvedRef == null`(凍結できる rev がまだ無い)、
  2 パス目で `flake.lock` の rev、3 パス目が `cmp` で不動点。
  `checks.resolve-merge`(`flake.nix:1663-1677`)がプラグイン側でやっているのと同じ形であることを名指しする。
  `prev.lazyNvim` を読まないと 2 パス目が null のままになる、というのがこの半分の存在理由である。

  **`raw-spec-pin.json` の lazy.nvim は `build = false` を持ち、各パスの stderr が空であること
  (`[ ! -s pass1.log ]`、`checks.resolve-sources` の `if [ -s ok.log ]` と同じ形)を assert する。**
  これが §3.4 (i)(警告条件は `p.build ~= nil` ではなく `classify_build(p.build).kind ~= "none"`)の
  唯一のガードである。`p.build ~= nil` と書かれていると
  「`build` is ignored」という**嘘の警告**がここで 1 件出て落ちる。
  `false` は lazy 自身の "do not build" なので、そこに「無視した」と言うのは事実に反する(§3.4)。
- **(3) version**: `mkTagRepoSh` の `mkrepo` でローカル repo を **4 本のタグ**(`v11.0.0 v11.14.0 v11.14.1 v12.0.0`)
  で作り、`jq` で url を注入。`resolvedRef == "refs/tags/v11.14.1"` と、生成 flake の `?ref=refs/tags/v11.14.1`。
  範囲外の `v12.0.0` を repo に置くのは「最新タグを取るだけの実装なら通ってしまう」を防ぐため
  (`checks.resolve-golden` の `v2.0.0` と同じ意図。`flake.nix:2887-2888`)。
  **`docs/plans/23-resolve-semver.md:235` の申し送りに答えているのがここである**ことをコメントに書く。
  ここは github type では書けない: `resolve.lua:812` が github type で `p.url` をそのまま ls-remote に渡すため、
  ローカル repo に差し替えられない(`checks.resolve-golden` が同じ制約下にある)。

  **続けて、同じ repo に 5 本目のタグを打ってから `--prev` 付きで `--update lazy.nvim` を走らせ、
  `refs/tags/v11.14.9` へ動くことまで見る。** 3 つの要素がすべて必要である:

  ```bash
  # (3a) 4 本で解決 -> v11.14.1
  mkrepo $sb/lazy v11.0.0 v11.14.0 v11.14.1 v12.0.0
  jq --arg u "file://$sb/lazy" '.plugins["lazy.nvim"].url = $u' $fx/raw-spec-version.json > vin.json
  nvim -l $lua/resolve.lua vin.json v1.json --lazy $lazy 2> /dev/null
  jq -e '.lazyNvim.resolvedRef == "refs/tags/v11.14.1"' v1.json > /dev/null

  # (3b) 上流に新しいリリースが出た、を再現する 1 行。mkrepo は repo を作る関数で、
  #      既存の repo にタグを足す口を持たないので素の git tag -a を書く
  git -C $sb/lazy -c user.name=nvimx -c user.email=nvimx@example.com tag -a v11.14.9 -m v11.14.9

  # (3c) --prev がここでの主語である。前回の決定が無ければ force は捨てるものが無く、
  #      force の有無に関わらず再解決されてしまい、摂動 (d) が検出できなくなる
  nvim -l $lua/resolve.lua vin.json v2.json --prev v1.json --lazy $lazy \
    --update lazy.nvim --update-plan plan-v.txt 2> /dev/null
  jq -e '.lazyNvim.resolvedRef == "refs/tags/v11.14.9"' v2.json > /dev/null
  [ "$(cat plan-v.txt)" = "lazy-nvim" ]
  ```

  - **4 本で始める**のは `version.lua:81-84` の `Semver.last(matched)` が最新を返すからである(§3.7)。
    5 本で始めると (3a) が `v11.14.9` になり、`v11.14.1` の assert がその場で落ちる。
  - **(3b) の `git tag -a`** が 5 本目を作る。`mkrepo`(`flake.nix:183-194`)は `git init` から始める関数なので、
    同じディレクトリに 2 度呼べない。
  - **(3c) の `--prev v1.json`** が無いと `force` の有無で結果が変わらず、
    §3.6 の `force` 1 行を削除しても check が緑のまま通る(§6.3 (d))。
- **(4) collide**: 非ゼロ終了、`plugins.json` が作られないこと、`[nvimx] resolve failed: plugin ` が 2 行、
  `LC_ALL=C sort -c` で名前順であること、予約名側の行が `reserved for lazy.nvim itself`、
  プラグイン同士側が `derived from more than one plugin` を含むこと。
  `checks.resolve-sources` の reject 半分(`flake.nix:2821-2857`)と同じ形。
  **2 行を数えることが本質**である: 予約名衝突だけを見ると、プラグイン同士の衝突が
  `error()` から `fail_plugin` に移った回帰(摂動 (n))を捕まえられない。

  **このステップには `--lazy $lazy` を渡す。** `raw-spec-collide.json` の予約名側エントリは
  `version = "^1.0"` と到達不能な `url = "file:///nvimx-nonexistent/lazy-nvim"` を持っており、
  §3.9-4 の「衝突した plugin を semver ゲートに積まない」の**予約名側**(決定的な方)を
  この 2 行だけで固定する(摂動 (o))。**`--lazy` を渡さないとこのガードは働かない** ——
  実測すると、抑止を消した実装に `--lazy` 無しで走らせた場合
  `resolve.lua:852-854` の `report_resolve_errors()` が先に `os.exit(1)` するので
  `fail("a version constraint needs --lazy ...")` に到達せず、
  `resolve failed: plugin ` の行数は 2 のままになる:

  ```console
  ### 抑止を消した実装、--lazy あり(= 摂動 (o) が捕まる)
  nvimx-lock: resolving version constraints for 1 plugin(s)
  [nvimx] resolve failed: plugin "foo-nvim": flake input name "foo-nvim" is derived from more than one plugin (foo-nvim, foo.nvim); ...
  [nvimx] resolve failed: plugin "lazy-nvim": flake input name "lazy-nvim" is reserved for lazy.nvim itself; ...
  [nvimx] resolve failed: plugin "lazy-nvim": git ls-remote failed for file:///nvimx-nonexistent/lazy-nvim (exit 128): fatal: '/nvimx-nonexistent/lazy-nvim' does not appear to be a git repository / ...

  ### 同じ実装、--lazy なし(= 3 行目が出ず、摂動が素通りする)
  [nvimx] resolve failed: plugin "foo-nvim": ...
  [nvimx] resolve failed: plugin "lazy-nvim": flake input name "lazy-nvim" is reserved ...
  ```

  正しい実装では `pending` が空なので **stdout に `nvimx-lock: resolving version constraints` が 1 行も出ない**。
  これも assert する(`! grep -q 'resolving version constraints' collide.out`)。
  `file:///nvimx-nonexistent/...` は既存の慣習(`tests/fixtures/semver/`、`update/`、`import-lazy-lock/`)で、
  ネットワークを一切使わず `git ls-remote` が即座に exit 128 するので
  `LS_REMOTE_TIMEOUT_S`(60 秒)には掛からない。

- **(5a) pin × `update_all` の plan**: `raw-spec-pin.json` に `--update --update-plan` を渡し、
  update-plan が `lazy-nvim` を**含まない**こと(§3.6 の非対称の解消)。
  同じ raw-spec に `--update lazy.nvim` を渡すと `lazy-nvim` が入ることも見る
  (「名前指定は pin を上書きする」が通常プラグインと同じ規則であること)。
- **(5b) `dev` × `pin` の除外**: `raw-spec-devpin.json`(`lazy.nvim` が `dev = true` + `dir` + `pin = true`)に
  `--update --update-plan` を渡し、update-plan が `lazy-nvim` を**含む**こと。
  **これが `lazy_is_spec` の `dev`/`dir` 除外を守る唯一のガードである**(§6.3 (i)):
  除外を落として `lazy_pinned = is_true(lp.pin)` と書くと `lazy_pinned` が真になり、
  合成 seed input が no-names update から落ちて `docs/architecture.md:274` の #24 契約が破れる。
  `resolve.lua:660-666`(全体更新の force 集合)は既に `not (p.dev or p.dir)` を持っているので、
  **壊れるのは plan writer 側だけ**である —— その主張をこのステップが固定する。
  あわせて `.lazyNvim.synthetic == true` と `.localPlugins` に `lazy.nvim` が居ることも見る
  (`dev`/`dir` が `is_lazy` より優先される、という §3.4 の分岐順序の固定)。

### 手動確認(check にできない部分)

**オンラインでの実 lock を 1 回通すこと。** 本件が直すのは `nix flake lock` まで到達する経路であり、
check はそこに届かない(ビルドは完全にオフライン)。`nvim/init.lua` に
`{ "folke/lazy.nvim", version = "*" }` を書いた config を作り:

```bash
nix run .#lock -- --config ./nvim --out ./nvim/nvimx-lock
```

確認すること:

1. **成功して終わること。** 従来はここで `error: attribute 'lazy-nvim.url' already defined` で落ちていた(§1.1)。
2. `nvim/nvimx-lock/flake.nix` の `lazy-nvim` input が **1 つだけ**で、URL が `github:folke/lazy.nvim/refs/tags/vX.Y.Z`
   (`version = "*"` が解決した実タグ)になっていること。**github type + `version` を通す唯一の経路がここである**(§7)。
3. `nvim/nvimx-lock/plugins.json` の `plugins` に `lazy.nvim` が**居ない**こと、`lazyNvim.synthetic` が `false` であること。
4. `nvim/nvimx-lock/flake.lock` の `lazy-nvim` ノードがそのタグの rev を指していること。
5. 続けて `nix build .#demo` 相当のビルドが通り、`:Lazy` で lazy.nvim が 1 つだけ local 表示されること
   (farm に 2 つ入っていない = §1.4 の last-wins を踏んでいないことの確認)。
6. **もう一度同じ lock を実行して `git diff` が空であること**(2 パス収束の不動点。§3.5 の `converged` の実 lock 版)。

`{ "someone/lazy-nvim" }` を書いた config で `nix run .#lock` が
`[nvimx] resolve failed: plugin "lazy-nvim": flake input name "lazy-nvim" is reserved for lazy.nvim itself; ...`
で止まり、`plugins.json` が書き換わっていないことも 1 回確認する。
